Internal · QA Automation

QA AI Skills · High-Level Design

How the skills learn a Robot Framework repository, generate and prove scripts, and measure automation coverage against the development code.

1. Purpose and scope

QA teams spend most of their automation time on work a machine can do reliably once it understands the repository: finding the right keyword, the right locator, the right login and route, then running and fixing until the test is stable. QA AI Skills does that work inside the team's own AI editor, using the team's own code as the source of truth, and leaves the decisions (approval, commit, release) with people.

Goal 1 · Quality that never drops

Reuse before creating; prove every new locator live; two passes on the same code; never weaken an expected result; full knowledge, checked for completeness.

Goal 2 · Speed

Scripts write the facts and the AI only the meaning; batches; resume; draft-first for known steps; runs that never hang; one-call handover.

Goal 3 · Measurable coverage

A coverage map, gap analysis and regression gap analysis built from evidence: what the code contains against what the tests really do.

Goal 4 · Enterprise safety

Read-only by default, approvals for every change, no secrets or client data anywhere, nothing leaves the machine except through the editor already in use.

In scope

  • Robot Framework repositories using SeleniumLibrary (including Selenium2Library) and/or the Browser library; Robot Framework 3.2 and newer.
  • Editors: Devin Desktop, VS Code with GitHub Copilot, VS Code with Claude Code.
  • Test case input: Markdown and text files in many layouts, CSV exports, qTest (read-only), mock screens, plain requests.
  • Optional development repositories (read-only), old and new front-end and back-end frameworks.

Out of scope

  • Changing development code, building it or deploying it.
  • Production environments.
  • Writing to qTest or any test management tool.
  • Automatic commits, pushes or merges.

QA repository

  • Parsing uses Robot Framework's own parser (3.2 and newer), so every suite format Robot accepts is read the same way: .robot, .resource, .txt, .tsv, pipe-separated. Files the installed Robot cannot parse are listed, never dropped.
  • Parallel and resumable: changed files are parsed in parallel processes when there are 200 or more; a content-hash cache skips unchanged files; progress is saved every 250 files.
  • Libraries per suite are traced through shared resources; Selenium2Library and its extended variants are treated as SeleniumLibrary.
  • Run configuration is read, not assumed: vault loaders, .env, variable files, command-line variables, argument files, suite setups.

Development code

A front end is detected from build files and from the page files themselves, so older applications without a package.json are found. Pages are read the same way whatever the framework.

Understanding test cases

  • Indexing: tc_reader.py finds test cases in any layout (story headings over test case headings at mixed levels, Gherkin scenarios, numbered titles, bold IDs, one table for all, CSV). It checks the count against the file's own index and names any IDs or headings it did not read.
  • Packets: the AI reads each test case once, with only the catalog rows it uses and the file's reading rules.
  • Cards: a structured understanding (goal, data, steps with marks ➕ added, ≈ made concrete, ⚠ check) is rendered by script as one card per test case, never as a paragraph.
  • Changed checks: any check that differs from the test case's exact expected result is recorded with tc_reader.py change, shown as ⚠ on the card, and blocks verification until the user's OK.
  • Learning: steps and catalog names proven in passing runs are saved (names only, never data) and reused by later test cases.

Draft first, explore only what is new

A test case whose every step is covered by existing keywords (with the screen's proof element in the app map) is written straight from the knowledge and goes to run 1, which is its proof. Only test cases with new steps open the live session, and only to reach the first new screen and prove its new elements. A known step that fails in run 1 is diagnosed first, then inspected live from the last passing step.

Locator strategy

  1. Existing team locator, then one created earlier in the batch.
  2. From the development code: test ID, then a stable id or name, then label or visible text.
  3. From the screen's controls list in the live session.
  4. Playwright, only if still needed.

Auto-generated ids are rejected. Every new locator is proven in the live session in one call and rated Strong, Good or Weak; Weak ones carry the test ID to ask developers for. Stale team locators are reported as suggestions, never changed.

Quality gate (script_check.py)

Blocks

Sleep, secrets, URLs or client data in code, AI helper libraries, inline locators, fragile locators, missing result checks, SQL writes and shared-data changes without restore, missing ai-generated tag, dry-run errors.

Warns, settled by the AI

Reuse warnings (existing keyword or locator does the same; the AI reuses or writes # kept new: reason), checks that ignore case or spacing (must be recorded as changed checks), possible data changes.

Style

The repo's Robot version syntax (:FOR/Run Keyword If on 3.x up to VAR on 7), the library imported exactly as the suite does, the repo's file format.

→

ai_run finalNext run: only tests short of two passes

Run watchdog

The listener writes a heartbeat next to the results: the running test, the stack of open keywords with start times, each step's own wait limit, and the locator a click or wait acts on (never typed values).

RuleDetail
Allowance for the deepest running stepThe largest of: 3 × its slowest earlier time (and at least that + 60 s); its own wait limit + 60 s; for a step never seen, the library's limit (page load timeout, 300 s by default for SeleniumLibrary; action timeout for Browser) + 60 s
Moving, never stoppedAny keyword starting or ending resets the clock, so polling loops and retries are never treated as stuck
ConfirmationOver the allowance on two looks at least 30 s apart, with no event in between
EvidenceThe step, how long, the allowance and its basis, the API and outside systems behind the element (development knowledge), and the optional health URL's answer
Stop ladder1 · stop request → the listener raises an interrupt inside Robot (like Ctrl+C: the test fails, teardowns run, output is written) · 2 · after 60 s a second request forces the stop · 3 · after 120 s the process tree is ended
ClassificationThe test is BLOCKED (environment), not FAIL: no fix attempt, no script change; tests using the same step wait; others can run; a run without complete output is rebuilt from the heartbeat

Two-pass proof

Each run records, per test, a fingerprint of everything the test executes: its own lines, the keywords and variables it uses (resolved transitively, including embedded-argument keywords) and its suite's setup and teardown lines. A pass counts only while that fingerprint is unchanged. final lists the tests still short of two passes and prints the --test options for exactly those; skipped and blocked tests are not rerun. When the team marks tests parallel-safe in run-config.md and pabot is installed, it prints a pabot command instead.

Promote and handover

  • Promote moves proven tests from drafts/ to verified/, with exactly the keywords and variables they use; drafts keep only the rest and import the verified resource; DRAFTS-NOTE.md records why each remaining test is there and what it needs.
  • Summary: where the time went, the runs in plain words, fix attempts, locator sources and ratings, slowest steps, runs not completed.
  • Faster code suggestions are mandatory: each slow keyword's existing code next to a complete faster version; the check fails while one is missing; suggestions survive a rewritten summary.
  • finish does the whole handover in one call and refuses while a test still needs a pass.

7. Coverage engine

coverage.py measures automation against the development code. It is deterministic, read-only, standard-library Python, and produces a manager summary, a gap list, an Excel matrix, an offline HTML report, a JSON snapshot (for trends) and test cases for the top gaps.

IDs are built from routes, element keys, class and method names and message text, not line numbers, so they stay stable across builds. Each item carries its source file and line and a fingerprint of its defining facts.

Evidence model

  • Every automated test is expanded through its keywords, binding positional, named and default arguments and resolving variables and locators, down to the library actions it performs (memoised per keyword and argument set).
  • Actions are classified: set a value, click, check shown, check hidden, check disabled, check text, navigate. Run Keyword ... wrappers are unwrapped; Run Keyword And Expect Error marks a negative test.
  • Locators are reduced to tokens (id, test ID, name, model binding, partial id, visible text) and matched to development elements.
  • Per test the engine keeps: elements touched and how, checked texts, value lengths and option names (never values), a fingerprint of the user who logged in, and intent words (negative, role-negative) from names and documentation.

Status rules (summary)

ItemCovered whenPartial when
FieldA test sets a valueTests only look at it
ButtonA test clicks itTests only check it is there

Coverage % = (Covered + ½ Partial) ÷ testable items. Items reachable only by API are N/A and reported separately. Decisions in decisions.md (<ID> | <status> | <reason>) override the computed status on every build and are marked in every report.

Priority

Score = base weight by type (business rule and role rule 32, outside system 30, status change 26, screen 26, API 18, rule 18, condition 16, server validation 14, message 14, field and button 12, options 6) × 1.0 for a Gap, 0.8 for a Partial on a risky item (outside system, business rule, role rule, status change), 0.55 for other Partials; plus up to 20 for recent code changes (4 per commit in 180 days, first import excluded), 8 for money or personal-data fields, 6 for items behind outside systems, and 4 per outside-system call on an unreached screen. P1 ≥ 30, P2 ≥ 18, else P3. The reasons are written next to every gap.

Regression gap analysis

  1. git diff --unified=0 base..head on each development repo gives changed files and line ranges.
  2. An item is changed when its source line falls in (or within 3 lines of) a changed range; a screen when any of its files changed; an outside system when its client changed, which also marks every API call that uses it.
  3. Tests to run = the proving tests of every changed item, plus tests that reach changed screens.
  4. Regression gaps = changed items that are Gap or Partial, ranked by priority.

Without git history, the JSON snapshot still gives "changed since the last build" from item fingerprints. If a ref is missing from a shallow clone, the exact fetch command is shown and the user is asked before it runs.

8. Installer

  • One command on Windows, macOS and Linux; registers qa-ai-setup on the user's PATH without admin rights; Devin is the default editor.
  • Chosen editor only: MCP settings and slash commands for that editor; anything an earlier install created for another editor is removed (only exact copies of its own files), with backups in qa-ai-skills/backup/.
  • Merge, never replace: only its own entries are added to MCP files; user entries, comments and formatting are kept; an entry of the user's with the same name is reported, not replaced; committed team files are left alone.
  • qTest: URL, project and token source (paste, masked, saved only to .env; or a vault key name), with Back at every question.
  • Proof: every MCP server is started once and every self-test runs; coloured status lines with cause and fix; check changes nothing.

10. Security and compliance

  • Read-only by default: team tests, keywords and locators are changed only after approval; development repos are never changed, built, installed or committed; qTest is read-only.
  • Secrets: only from the vault, configuration or .env; never typed into chat, shown, logged, or written into code, comments, tags, knowledge, metrics or reports; a pasted token is masked.
  • Client data: no client IDs or data values in generated code, knowledge or reports; coverage keeps lengths and option names only; user identities in coverage are fingerprints.
  • Environments: test environments only; production-looking targets stop the run.
  • Data safety: exploration never clicks Save, Submit, Delete or Approve; tests that change shared data restore it in teardown; a stopped run still runs its teardowns.
  • Change control: asks before adding to suites, branching, committing or pushing; drafts and session files are never committed; MCP settings with machine paths are git-ignored.
  • Offline outputs: the HTML reports load nothing from the internet; no telemetry.
  • Transparency: plain-text Python and Markdown, no compiled or encoded code, so security teams can review everything.

12. Known limits and next steps

Known limits

  • Development facts are static: screens built entirely at run time and rules kept only in a database are not seen.
  • Coverage matching relies on ids, test IDs, names, model bindings and visible texts; tests that act only through generic XPath may be under-counted (corrected through decisions).
  • Frameworks that build screens in code (Vaadin, GWT, Wicket) are read from their page files only; their screens are found live during generation.
  • Robot Framework older than 3.2 cannot be parsed for the knowledge build (a newer Robot in a separate environment can be used just for the build).
  • An editor's own action limit (for example Devin's Continue) is outside the skills' control.

Next steps (planned, not built)

  • Distribution as a Python package through the company's internal package repository (one install command, scanned and versioned).
  • Optional enabling of the editor's auto-continue setting from the installer, once its storage is confirmed.
  • An API-test generator for items marked N/A in coverage.
