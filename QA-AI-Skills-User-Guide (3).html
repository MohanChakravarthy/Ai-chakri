Internal · QA Automation

QA AI Skills · User Guide

Turn test cases into proven Robot Framework scripts, and see exactly what your automation covers, in Devin, VS Code with GitHub Copilot, or VS Code with Claude Code.

1. What it is

QA AI Skills is a set of AI skills and helper scripts that live in one folder, qa-ai-skills/, at the root of your Robot Framework QA repository. They learn your repository from its own code, then write new test scripts the way your team writes them: with your keywords, your locators, your login and your run command. Every new script is proven by real runs before you are asked to keep it.

@qa-knowledge-setup

Learns your QA repository (tests, keywords, locators, how tests run) and, optionally, your development code (screens, fields, rules, APIs). Also builds the coverage map and the regression gap analysis.

@robot-script-generator

Turns one test case, a whole test case file, a qTest ID, a mock screen or a plain sentence into Robot Framework scripts that pass twice in a visible browser.

qa-ai-setup

The one-command installer. Connects the AI tools (MCP servers) for the editor you choose, optionally qTest, and checks that everything works.

What you get

  • Scripts that look like your team wrote them: existing keywords and locators first, new locators only when needed, each one proven on the live page and rated Strong, Good or Weak.
  • Proof, not promises: a script counts as passed only after two passing runs on the same code, in a visible browser.
  • Clear understanding before any work: each test case is shown as a card, step by step, with what was added or made concrete marked for you to check.
  • Coverage you can measure: what your automated tests really cover, compared with what the development code contains, with every gap ranked and turned into a suggested test.
  • Safe by design: your tests are never changed without your approval, nothing is committed without asking, secrets never appear in code or chat, and the development repo is only read.

3. Install (once per computer)

  1. Copy the qa-ai-skills/ folder into the root of your QA repo (replace an older one).
  2. Open a terminal in the root of your QA repo and run the installer:
    SystemFirst timeAfter that (any folder in the repo)
    Windows (PowerShell or Command Prompt).\qa-ai-skills\qa-ai-setup installqa-ai-setup install
    macOS / Linuxsh qa-ai-skills/qa-ai-setup.sh installqa-ai-setup install
  3. Choose your editor with the arrow keys and Enter: Devin Desktop (the default), VS Code with GitHub Copilot or VS Code with Claude Code. Only that editor is set up.
  4. Answer the qTest question (optional, see below).
  5. Read the Next steps it prints, restart the editor, and confirm the AI tools show as connected.

What the installer does

  • Picks the Python that has Robot Framework: the active virtual environment, else the repo's .venv or venv, else the system Python.
  • Installs the Robot Framework MCP (rf-mcp) and the Playwright MCP only if they are missing.
  • Writes the MCP settings for your editor inside this project (git-ignored, because they hold paths of this computer): .devin/mcp_config.local.json for Devin, .vscode/mcp.json for Copilot, .mcp.json for Claude Code.
  • Adds the slash commands for VS Code (/robot-script-generator, /qa-knowledge-setup) and the git-ignore lines.
  • If an earlier install set up a different editor, removes only the files it created for that editor; your own files are never touched. Backups go to qa-ai-skills/backup/.
  • Starts every AI tool once and runs every self-test, so you know it works before you use it.
  • Registers the qa-ai-setup command (no admin rights needed; open a new terminal to use it).

Every line shows a coloured status: [ OK ] [WARN] [FAIL] [SKIP]. Every warning and failure says the cause and the exact fix, and they are repeated in the summary under Action required.

Run it again any time. It only redoes what is missing. qa-ai-setup check checks everything and changes nothing; qa-ai-setup help lists every option.
Your own settings are safe. Your other MCP servers, comments and formatting stay exactly as they were. An entry of yours with one of our names is never replaced; it is reported instead. Every file changed is backed up first.

Connecting qTest (optional)

With qTest connected, @robot-script-generator qtest TC-1328 reads the test case straight from qTest. It is read-only: nothing is created or changed in qTest.

  1. Answer Yes to the qTest question and enter your qTest address and project ID.
  2. Choose where the token comes from: paste it now (it shows as * and is saved only in the git-ignored .env file) or read it from your vault by its key name, for example QTEST_TOKEN.
  3. Changed your mind? Type B at any qTest question, or choose Back: skip qTest for now. Nothing is saved, and setup continues. You can connect qTest later by running the installer again.

Check it any time with python qa-ai-skills/skills/qtest/qtest_mcp.py --check: it shows your project name and where the token came from, never the token itself.

What you see

A 7-step checklist appears in the editor's own task list and ticks itself as it goes. The chat gets one short line per finished step, with its result and time.

✅ 2. Learned the development code - 38 screens, 610 fields, 140 rules (1m 12s)

⬜ 5. Building the locator knowledge

Marks: ✅ done, ⏳ in progress, ⬜ waiting, ⏭ skipped, ❌ stopped (with the reason).

How it stays fast without losing quality

  • Scripts write the facts, the AI writes the meaning. Every keyword, locator, route and run setting is read by scripts in seconds, with no AI tokens. The AI writes only short meaning lines (what a keyword does, which screen, which flow).
  • Batches, most-used areas first. Shared keywords that many areas use come first, then the biggest areas. Small areas are grouped into one pass.
  • Saved after every batch. If anything stops, a refresh continues where it was. Unchanged areas are never redone.
  • Proven complete. A coverage check proves that every keyword, locator and test file is in the knowledge, and a reviewer checks the meaning against the code.

Adding the development repos (optional, read-only)

On build and rebuild, the AI asks in one question for your development repo links (up to 10 at a time). A branch link (.../tree/<branch>) also gives the branch; for the others it lists the branches and asks once. You never have to say which repo is front end or back end; that is worked out from the code.

Each repo is cloned as it is into dev/<repo name> next to your QA repo (never inside it), using your normal git sign-in. Nothing in it is ever changed, built or committed.

From the development code a script records, for every screen:

  • fields, test IDs, labels, dropdown options and validation rules;
  • fields that appear, become required or are disabled only in some cases;
  • which button makes which server call, and what the screen shows after Save;
  • business checks with the message the user sees, which role may do what, status flows;
  • outside systems the back end calls (for example BMC or Alfresco), and which buttons reach them.
Old and new code alike. Older front ends with no package.json (AngularJS 1.x inside Spring Boot, JSP, JSF, Struts, ASP.NET Web Forms, plain HTML with jQuery) are read the same way as React or Angular. If a front end gives no screens, the AI says which repo and continues; it never calls a repo with pages "back end only".

Large repositories

From one suite to tens of thousands of tests, the build never makes the editor wait on one long command. Long steps run in the background and the AI checks on them in short calls, posting lines like:

Batch: MOD-COMMON, MOD-KYC (12 of 340 areas done, about 25 min left)

Finished areas can be used for script generation before the whole build is done. If a script needs an area not built yet, the generator builds that area's knowledge first, so nothing is used half-built.

Check run-config.md (once)

Open qa-ai-skills/knowledge/run-config.md after the first build and confirm:

  • the normal run command, the environments, and the library each suite uses;
  • how secrets are loaded (vault, .env, variable files) and through which file;
  • anything listed under Open questions.

Three settings your team may set:

SettingDefaultWhat it does

health urlnoneA page of the test environment that answers when it is up. Helps tell an environment problem from a script problem.

The 9-step checklist

Robot script for TC-1234 - progress
✅ 1. Read your test case - 5 steps found, 2 added from knowledge
✅ 2. Understood the test case and matched the steps - 4 reused, 1 new
⏳ 3. Checking the environment and logging in
⬜ 4. Opening the screen
⬜ 5. Reading the new screen
⬜ 6. Checking the new fields
⬜ 7. Writing the script and checking it against the quality rules
⬜ 8. Running the test (run 1 of 2)
⬜ 9. Running the test again (run 2 of 2) and finishing

Steps 5 and 6 are skipped (⏭) when every step is already known.

Test case cards: check the understanding first

Before anything runs, each test case is shown as a card, one per page, with every step and its expected result. Each step is marked:

MarkMeaningExample
(none)Taken from your test case as writtenClick Save
➕Added from the knowledge because the application needs itLog in as a maker; open the client first
≈Made concrete without changing the meaning"any subscriber" becomes "the first active subscriber"
⚠Needs your check: uncertain, conflicting, or changed from your test caseThe AVID is read from the page instead of the test case's 12345

Choose Looks right, next, Looks right, approve all, or I'll type a correction. The environment question (for example QA, Dev or UAT) comes last, as clickable choices. Your corrections are learned for next time.

Expected results are never weakened quietly. If the script has to check something different from your exact wording (for example "no result rows" instead of "empty results area", ignoring upper/lower case, or a value read from the page), it appears on the card as a ⚠ changed check, and that test counts as verified only after your OK.

How it builds the script

Reuse firstYour keywords and locators, then ones created earlier in this batch, then new ones
→
Known stepsWritten straight from the knowledge, no page exploration
→
New screens onlyRead live: development code, then the screen's controls, then Playwright
→
Every new locator provenOn the live page, rated Strong / Good / Weak
→
Quality gateNo Sleep, no secrets, no fragile locators, every test checks a result, dry run
  • One login for the whole request; the known route is followed in one call.
  • Your style: the syntax your Robot version runs, the library imported the way your suites import it, and your file format.
  • No duplicates: if a new keyword does the same as an existing one, the AI reuses the existing one when it can take the target as an argument; otherwise it keeps the new one and writes why. It never asks you about this.
  • While reading a screen it never clicks Save, Submit, Delete or Approve.

Runs and the two-pass proof

All test cases of a request go into one suite, so one login serves them all. Each test must pass twice on the same code in a visible browser:

  • A pass counts only while the test's own lines, the keywords and variables it uses, and the suite setup are unchanged since that run.
  • Fix rounds rerun only the failed tests. The next run holds only the tests still short of two passes; skipped tests and tests already proven twice are not rerun.
  • Up to 3 fix attempts per test, each diagnosed before anything is changed.
Example run line in the summary
3 Robot runs: run 1 (all tests): 3 passed, 2 failed, 1 skipped, 7m 05s; run 2 (only the 2 that needed it): 2 passed, 1m 40s; run 3 (only the 5 that needed it): 5 passed, 6m 10s.

A yellow badge in the browser shows the AI is running the test. A blue badge means rf-mcp is exploring, purple means Playwright is reading. There is no badge when you run a test yourself.

When the environment hangs

Every AI test run runs in the background and is watched, so a stuck integration never freezes the editor or waits forever.

  • Slow is not stuck. The step running right now may take the longest of: 3 times its slowest earlier run plus a minute, its own wait limit plus a minute, or, for a step never seen before, the page load limit plus a minute. A step that keeps retrying or polling is moving and is never stopped.
  • Only a silent step is stopped, after two checks at least 30 seconds apart. It is stopped safely, like Ctrl+C: the test fails, its teardown still runs and restores shared data, and the results file is still written.
  • It is not a script failure. The test is marked BLOCKED, uses no fix attempt, and the script is not changed. Tests that use the same step wait; the others continue.
Example
Environment problem: test 3 (TC-103) - step 'Submit Book Request' > Click Element got no response for 6m 10s (allowed 6m 0s: no earlier time: the library's own limit (5m) + 1 min). Not a script failure; no fix attempt used. It calls POST /api/book-requests/submit, which uses BMC, Alfresco (development knowledge): the likely cause is that service, not the script.

You are asked once: Retry it now or Leave it in drafts. The blocked test stays in drafts with its rerun command, and the summary lists it under Runs not completed with the two-run proof still pending.

Results and handover

  • Drafts and verified: work happens in ai_generated_tests/drafts/. Tests that passed twice are moved (not copied) to ai_generated_tests/verified/ together with exactly the keywords and variables they use. Drafts keep only what did not pass, with a DRAFTS-NOTE.md saying why each test is there and what it needs.
  • Summary report: written for a manager first: the goal, how the test case was understood, reused versus new steps, new locators with their ratings, both run results, data changed and how to reset it, notes for you, and the time taken.
  • Where the time went: time per step, every run, and the slowest keywords with the cause.
  • Faster code suggestions: for each slow keyword, your existing code next to a faster version (for example waiting for the next element instead of a fixed Sleep, or one login per suite). These are suggestions only; your keyword is not changed.
  • Your approval: the AI asks before adding the test to your suite, before creating a branch and before committing.

6. Many test cases at once

Give a test case file and say which ones: all, first 10, next 10, failed, 5-20, TC-101 TC-102, test case 3, or words from a title.

  • A script indexes the file first (no AI tokens) and reports how many test cases it found. If the file's own index lists more than it read, it names the missing IDs and their lines, and the AI reads those directly; a batch with fewer test cases than the file holds is never reported as complete.
  • Each test case is understood once and shown as a card. Test cases whose steps are all known are written straight away.
  • Runs go in groups of 10; passing tests move to verified after each group.
  • Repeated steps ("Open the client page for ...") are remembered after their first passing run and reused by every later test case.
  • At the end: the batch report, any changed checks waiting for your OK, the summary, and one approval question.

7. qTest, mock screens and plain requests

From qTest

@robot-script-generator qtest TC-1328 reads the test case, its steps and expected results from qTest (read-only) and saves a copy under ai_generated_tests/test_cases/.

New features on a mock screen

Add mock <link or .html file>. The route to the new feature is checked on the real application; the new part is read from the mock and proven there. The real test is reported as "waiting for release" until the feature is deployed.

Plain requests

Type what you want to check in plain words. The AI restates it as steps on a card and asks you to confirm before writing anything.

8. Coverage map and gap analysis

@qa-knowledge-setup coverage answers: how much of the application do our automated tests really cover, what is missing, and what should we automate next? It needs the development knowledge (section 4).

How it works

What the code containsScreens, fields, buttons, rules, conditions, roles, business rules, status changes, API calls, outside systems, messages, options
→
What the tests really doEvery test traced through its keywords and arguments to what it types, clicks and checks
→
Matched by evidenceSame id, test ID, name, model binding or visible text
→
Status per itemCovered, Partial or Gap, with the reason and the proving tests

Example: Customer name is required (from the code). Test TC-101 fills it in, but no test leaves it empty. Result: Partial, "Only the valid path is tested", with the suggested test "Leave 'Customer name' empty and save; expect 'Customer name is required'."

Statuses

StatusMeaningExample
CoveredA test exercises it the way it mattersBreaks the rule and checks the message; checks both sides of a condition; tests with a user who lacks the role
PartialA test touches it, but only the easy pathThe field is filled, but no test leaves it empty; BMC is reached, but nobody tests what happens when BMC fails
GapNo automated test touches itA screen no test opens
N/AOnly reachable through an APINeeds an API test, not a UI test

Coverage % = Covered items + half of the Partial items, out of all testable items.

Kinds of gaps

GroupWhat is missing
Happy pathScreens, fields, buttons or calls no test uses
NegativeRequired fields left empty, invalid formats, business-rule messages, error messages
ConditionalFields shown, enabled or required only in some cases, tested on one side only
BoundaryMaximum and minimum lengths and values
Roles / securityActions allowed only for some roles, never tried with a user who lacks the role
IntegrationOutside systems (BMC, Alfresco ...): success and failure handling
Status flowStatus changes, and refusals from statuses that are not allowed
Data variationDropdown options never selected

Priority

Each gap is ranked P1 (fix first), P2 or P3 from: the kind of item (business and role rules, outside systems and unreached screens weigh most), money or personal-data fields, and how often its code changed in the last 180 days.

The reports

All in qa-ai-skills/knowledge/coverage/:

FileForWhat is in it
coverage-map.mdManagersCoverage %, counts, coverage by kind and by area, top 25 gaps, outside systems, manual versus automated, trend since last time
coverage.htmlAnyone, in a browserThe same, interactive and offline: tiles, bars by area, gaps by kind, a searchable list of every item
coverage-matrix.csvExcelEvery item: ID, area, status, priority, reason, proving tests, suggested test, source file
gaps.mdTestersEvery gap, grouped by kind, with a suggested test; manual test cases not automated yet
gap-test-cases.mdThe script generatorThe top gaps written as test cases (section 10)
decisions.mdCorrectionsItems checked by hand; these win over the computed status on every rebuild

Add with <test case file or folder> to also compare your manual test cases: which have an automated test, which do not, and which code items they would cover.

Limits worth knowing. Items come from what the code shows; screens built entirely at run time, or rules kept only in a database, are not seen. A test that acts only through generic XPath with no ids or texts may be under-counted. The AI checks doubtful P1 items and records its findings in decisions.md.

9. Regression gap analysis

@qa-knowledge-setup regression <release tag> compares two versions of the development code and answers two questions: which existing tests should we rerun, and what changed that no test checks.

A release tag is a bookmark developers put on the code when they release, for example release-24.3. A branch name or a commit ID works too. You can also name the newer side: regression main feature/kyc.

Example

Since release 24.3, developers raised the Customer name limit from 40 to 50 characters and reworded the BMC error message.

Result
Regression release-24.3..HEAD: 6 changed items; 2 regression gaps (P1 1); 2 existing tests to run.
Tests to run: TC-101 Create request, TC-102 Customer name too long.
Regression gaps: 'Customer name' maxlength 50 (Partial); Business rule: BMC rejected this request (Partial).

It writes regression-<base>-<head>.md and .html. If the older version is not in the local clone, it shows the exact command to fetch it and asks before running it; the development repo itself stays read-only.

10. Automating the gaps

@robot-script-generator gaps (or gaps top 10) reads gap-test-cases.md as a test case file. Each gap test case names the item it closes. Cards come first, as always, then scripts, runs and handover. Afterwards, run @qa-knowledge-setup coverage again and the map shows those items as covered, with the trend.

14. Safety rules (built in)

  • Read-only on your tests, keywords and locators until you approve a change.
  • Test environments only; it stops if the target looks like production.
  • Passwords and tokens come only from your vault or configuration; they are never typed, shown, or written into code, comments, tags, knowledge or reports. A pasted qTest token shows as *.
  • No client IDs or client data in generated code, knowledge, metrics or coverage reports (coverage keeps only lengths and option names, never values).
  • Never weakens your expected results; any changed check needs your OK.
  • Shared test data changed by a test is restored in its teardown.
  • While exploring a screen it never clicks Save, Submit, Delete or Approve.
  • The development repo is only read: never changed, built, installed or committed. Repo links are stored without user names or tokens.
  • Nothing is added to your suites, branched, committed or pushed without your answer. Drafts and session files are never committed.
  • Your other MCP servers and settings are never replaced; every changed file is backed up.

15. Questions and answers

Do I have to build the knowledge again every time?

No. Build once, then refresh after pulling new code. Only changed areas are redone.

Can I use it without the development repo?

Yes. Scripts are generated from your QA repo alone. The development repo makes new locators, waits and conditions stronger, and is needed for the coverage map and regression analysis.

Why does a test need two passes?

One pass can be luck. Two passes on the same code show the test is stable before you keep it.

Will it change my existing keywords?

No. It reuses them. If one is slow, the summary shows a faster version next to your existing code as a suggestion; your team decides.

What does the coverage percentage include?

Every testable item found in the development code. Covered counts fully, Partial counts half. Items that need API tests are listed separately and not counted.

Is anything sent outside our network?

The reports and knowledge stay on your machine and in your repo. The AI editor you already use sees what you work on, as it does today.
